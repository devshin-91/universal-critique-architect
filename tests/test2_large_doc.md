# [시스템 아키텍처 설계서] 글로벌 실시간 분산 결제 및 정산 플랫폼 (Project PayCore)
**작성자:** 엔터프라이즈 결제 코어 태스크포스  
**문서 버전:** v1.0.4  
**문서 상태:** RFC (Request for Comments)  

---

## 1. 개요 및 비즈니스 배경
본 문서는 전 세계 14개국, 분당 최대 120,000건(120k TPS)의 크로스보더 결제 및 환전 정산을 실시간으로 처리하기 위한 'Project PayCore'의 핵심 백엔드 분산 아키텍처를 정의한다. 
기존 레거시 모놀리식 결제 시스템은 블랙 프라이데이 및 대규모 프로모션 기간 동안 데이터베이스 커넥션 풀 고갈과 락 경합(Lock Contention)으로 인해 심각한 타임아웃 및 이중 결제 장애를 겪어왔다. 이에 따라 우리는 마이크로서비스 아키텍처(MSA)와 이벤트 기반 아키텍처(EDA)를 결합하여 99.999%의 가용성과 제로 데이터 유실을 보장하는 차세대 결제 코어를 구축하고자 한다.

---

## 2. 전체 시스템 아키텍처 및 데이터 흐름

### 2.1. 인그레스(Ingress) 및 API 게이트웨이 레이어
* 모든 클라이언트(모바일 앱, 웹 프론트엔드, 서드파티 가맹점 POS)의 요청은 AWS CloudFront 및 Cloudflare Enterprise CDN을 거쳐 글로벌 Anycast 기반 Envoy API Gateway 클러스터로 유입된다.
* API Gateway는 JWT 토큰 기반의 무상태(Stateless) 인증 및 mTLS 상호 인증을 수행하며, 가맹점별 초당 요청 수(RPS)를 감시하는 Redis 분산 토큰 버킷 레이트 리미터(Rate Limiter)를 통과시킨다.
* 유효한 결제 승인 요청은 즉시 비동기 이벤트 스트림으로 전환되기 위해 분산 트랜잭션 오케스트레이터로 전달된다.

### 2.2. 결제 오케스트레이션 엔진 (Saga Orchestrator)
* 크로스보더 결제는 복수 국가의 결제대행사(PG), 외환 환전소(FX Provider), 가맹점 원장(Ledger), 유저 포인트 시스템을 단일 트랜잭션으로 묶어야 한다.
* 우리는 2단계 커밋(2PC)의 분산 블로킹 문제를 회피하기 위해 오케스트레이션 기반 사가 패턴(Orchestrated Saga Pattern)을 채택한다.
* Saga 오케스트레이터는 Temporal 워크플로우 엔진 기반으로 구동되며, 각 단계(결제 승인 ➔ 외환 환율 고정 ➔ 가맹점 정산 원장 기록 ➔ 영수증 발송)가 실패할 경우 자동으로 보상 트랜잭션(Compensating Transaction)을 역순으로 트리거하여 최종 일관성(Eventual Consistency)을 달성한다.

### 2.3. 이벤트 백본 및 메시지 큐 레이어
* 모든 결제 이벤트 상태 변화는 Apache Kafka 클러스터(3개 가용 영역에 걸친 12개 브로커 노드)의 `payment-events.v1` 토픽으로 프로듀싱된다.
* 토픽 파티셔닝 키는 `merchant_id`와 `user_id`의 복합 해시값을 사용하여 동일 사용자의 결제 이벤트는 항상 동일한 파티션에 순서대로 적재되도록 보장한다.
* 데이터 유실 방지를 위해 프로듀서 설정은 `acks=all`, `min.insync.replicas=2`, `enable.idempotence=true`로 강제한다.
* 카프카 다운타임 발생 시의 비상 장애 격리를 위해 각 마이크로서비스 인스턴스는 로컬 디스크에 임베디드 RocksDB 기반의 Write-Ahead Log(WAL) 버퍼를 유지하며 카프카 재연결 시 자동으로 이벤트를 재전송한다.

## 3. 원장(Ledger) 서비스 및 데이터 영속성 계층

### 3.1. 불변 복식부기(Double-Entry) 원장 모델
* 금융 감사의 무결성을 위해 모든 거래는 불변(Immutable) 원장 테이블에 기록된다. 잔액(Balance) 칼럼을 직접 UPDATE하는 쿼리는 아키텍처적으로 엄격히 금지된다.
* 모든 회계 처리는 차변(Debit)과 대변(Credit)의 합이 항상 0이 되는 복식부기 레코드로 INSERT되며, 현재 잔액은 이벤트 소싱(Event Sourcing) 방식으로 과거 거래 내역을 실시간 인메모리 스냅샷과 프로젝션하여 산출한다.
* 데이터베이스 엔진으로는 CockroachDB(분산 SQL)를 사용하며, 격리 수준은 완전 직렬화 가능(Serializable Isolation Level)으로 고정한다.

### 3.2. 일관성(Consistency) 및 파티션 장애 대응 (CAP 정리)
* 네트워크 파티션 발생 시 금융 데이터의 특성상 가용성(A)보다 일관성(C)을 우선 선택(CP 시스템)한다.
* 3개 데이터센터 간 Raft 합의 알고리즘을 수행하며, 쿼럼(Quorum) 과반수를 확보하지 못한 서브클러스터는 즉시 읽기 전용 모드로 전환되어 가맹점 승인 트랜잭션을 거부하고 안전한 오류 응답(HTTP 503 및 재시도 헤더)을 반환한다.

## 4. 재해 복구(DR) 및 고가용성(HA) 전략
* **RPO (목표 복구 시점):** 0초 (Zero Data Loss). 동기식 멀티 리전 복제 구성.
* **RTO (목표 복구 시간):** 30초 이내. Route53 DNS 헬스체크 기반 글로벌 트래픽 자동 페일오버.
* **카오스 엔지니어링:** 매주 목요일 새벽 카오스 메시(Chaos Mesh)를 통해 랜덤하게 카프카 브로커 노드 및 DB 파티션을 강제 킬(Kill)하여 자동 복구 파이프라인을 정기 검증한다.

## 5. 알려진 기술적 과제 및 트레이드오프
1. **외환 환율 변동성 레이스 컨디션:** 실시간 승인 시점과 최종 배치 정산 시점 사이의 환율 변동으로 인한 외환 차손 발생 리스크가 존재하며, 이를 위해 15분 만기 환율 선물 락(Lock) 메커니즘을 적용 중이다.
2. **핫 파티션 문제:** 특정 초대형 글로벌 가맹점(예: 대형 게임사 결제 이벤트)으로 인해 특정 카프카 파티션에 트래픽이 쏠려 지연 시간(Lag)이 증가하는 현상이 관측되었으며, 솔트(Salt) 키 기반 서브 파티셔닝을 도입 검토 중이다.
